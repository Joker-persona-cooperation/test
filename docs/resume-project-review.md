# TaskPilot 简历项目评审与面试准备

## 一、总体结论

新版简历用 TaskPilot 替换“Vue3 通用后台管理系统”是正确的。旧项目偏常见练手后台，技术点多但业务辨识度低；TaskPilot 有清晰的业务闭环，也包含异步任务、请求并发、失败恢复、数据一致性等更能体现工程能力的问题。

当前 TaskPilot 描述整体真实、结构清楚，核心内容基本都有代码支撑。不过部分表述将前端行为、后端事务和系统整体能力写在同一句中，容易让面试官误以为这些都由前端单独实现。建议重点突出以下四项：

1. 异步 AI 解析业务闭环。
2. PDF 上传的分阶段状态与失败恢复。
3. 并发 401 下的单次刷新与请求重放。
4. 任务看板排序、乐观锁冲突和服务端权威数据回退。

同时，简历应尽量使用“问题—方案—结果”的表达，不要只罗列页面和功能。没有真实数据时不要虚构性能百分比，可以写清解决了什么异常场景、避免了什么重复操作。

## 二、旧项目点评：Vue3 通用后台管理系统

### 2.1 优点

- 动态路由、路由守卫、Pinia 联动、Axios 封装、ECharts 自适应，覆盖了后台项目常见能力。
- 每一条职责都有明确技术名词，面试官容易据此展开提问。
- `ResizeObserver`、菜单/面包屑/Tab 联动比单纯写“完成后台页面”更具体。

### 2.2 主要问题

#### 业务价值弱，同质化明显

“登录、菜单、标签页、用户管理、数据看板”几乎是所有 Vue 后台模板的标准功能。面试官很容易把它判断为课程项目或脚手架二次开发，难以形成记忆点。

#### 技术点是横向堆叠，没有核心难题

五条职责分别讲布局、动态路由、图表、状态管理、Axios，但没有一条回答“项目中最难的问题是什么”。面试官追问时，回答容易停留在 API 使用层面。

#### 权限表述需要谨慎

“动态路由 + 路由守卫”只能控制前端页面入口和用户体验，不能代替后端权限校验。如果菜单来自 Mock 数据或本地配置，应明确这是前端权限演示，不要表述成完整安全权限体系。

#### “提升效率/体验”缺少证据

“提升开发联调效率”“优化页面切换体验”属于泛化结果。若没有数据，可改为“减少页面层重复配置”“保证菜单、面包屑和标签页状态一致”，更可验证。

### 2.3 是否保留

如果简历只能保留两个项目，建议优先保留 TaskPilot 和一个能证明移动端/多端能力的项目，删除通用后台。如果目标岗位强依赖中后台，可把该项目压缩到 3 条，并把动态权限和 ECharts 性能作为重点，不要与 TaskPilot 重复强调 Axios、Pinia、布局。

## 三、TaskPilot 当前描述逐条评审

### 3.1 项目描述

原描述：

> 面向任务型文档的 AI 拆解与项目管理平台，支持文本粘贴及 10MB 内文字型 PDF 上传，将文档解析为交付物、关键要求、风险提醒与任务清单，并完成解析结果编辑、项目创建、任务看板管理的业务闭环。

评价：业务对象、输入、输出和后续闭环都写清楚了，是合格的项目描述。建议把“AI”具体化为“异步 AI 解析”，以便自然引出轮询、任务状态和失败重试。

可优化为：

> 面向任务型文档的 AI 拆解与项目管理平台。用户可粘贴文本或上传 10MB 内文字型 PDF，系统通过异步解析生成交付物、关键要求、风险提醒和任务清单，并支持结果校对、项目创建与看板式任务管理。

### 3.2 核心链路

原描述：

> 负责文档解析核心链路开发，打通“文档录入—创建解析任务—状态轮询—结果编辑确认—保存为项目”的完整流程，并接入真实后端接口。

评价：真实、清晰，应保留。“接入真实后端接口”对个人项目有价值，但表达略弱，可以用异步状态轮询、结果确认和项目生成等业务机制替代。

建议改为：

> 负责文档解析主链路，串联文档录入、异步任务创建、状态轮询、结果编辑与确认、项目生成等环节；按 `pending / processing / success / failed` 状态驱动页面，并提供超时停止和失败重试。

### 3.3 PDF 上传状态机

原描述：

> 基于组合式函数设计 PDF 上传状态机，覆盖文件校验、上传、服务端提取、任务创建、成功、失败及取消等状态；支持上传进度、AbortController 请求取消和分阶段重试，任务创建失败时复用已上传文档，避免重复上传。

评价：这是项目最有价值的一条，且实现支撑充分。`usePdfSubmission` 确实集中管理阶段、进度、取消和重试；创建任务冲突时还会查询文档的最新任务。

建议微调两点：

- “状态机”可保留，但面试时要说明这是用联合类型和显式阶段转换实现的轻量状态机，不是引入 XState 等状态机库。
- “服务端提取”是后端能力，前端负责展示该阶段，不要说成前端完成 PDF 文本提取。

建议改为：

> 将 PDF 提交流程封装为组合式函数，以联合类型管理校验、上传、服务端处理、任务创建、失败、取消和成功等阶段；接入上传进度与 `AbortController`，并在建任务失败时保留 `documentId`，重试时跳过重复上传，同时恢复服务端已有解析任务。

### 3.4 Axios 请求层

原描述：

> 封装 Axios 请求层，实现统一响应处理、业务错误分类、CSRF Token 回填及 401 无感刷新；通过共享刷新请求合并并发 401，避免重复刷新和请求竞态。

评价：方向正确，也是强亮点。代码中实际采用 `isRefreshing + pendingQueue`：首个 401 发起刷新，其他请求进入队列；刷新成功后注入新 token 并重试，失败则统一结束会话。

“共享刷新请求”容易让人理解成缓存一个 `refreshPromise`，而当前实现是布尔锁和等待队列，建议改成“单刷新锁 + 请求队列”。“避免请求竞态”略宽泛，可以明确为避免多个刷新请求并发导致 token 覆盖或会话轮换冲突。

建议改为：

> 封装类型化 Axios 请求层，统一剥离响应信封、分类业务错误并注入 Bearer/CSRF 请求头；针对并发 401 设计“单刷新锁 + 等待队列”，仅发起一次 refresh，成功后重放挂起请求，失败时统一清理会话并保留登录回跳地址。

### 3.5 任务看板与一致性

原描述：

> 开发项目任务看板，支持任务增删改、状态流转及拖拽排序；采用完整集合事务提交与失败回滚保证前后端顺序一致，并针对乐观锁冲突自动获取服务端最新数据。

评价：技术含量高，但需要修正边界。

- 前端提交的是项目内全部任务 ID 的有序集合；“事务”由后端接口实现，不应让人理解为前端事务。
- 当前所谓“失败回滚”不是保存前端快照后做本地逆操作，而是请求失败后重新拉取服务端权威顺序。
- 跨列拖拽目前先更新任务状态，再提交排序，它们是两个请求，并非一个跨接口原子事务。如果状态更新成功、排序失败，状态可能已经改变，但重新获取会恢复服务端真实状态和顺序。面试时必须准确说明。

建议改为：

> 开发三列任务看板，支持任务增删改、状态流转、拖拽及键盘按钮排序；前端每次提交项目内完整任务 ID 顺序，由后端事务统一重写 `sort_order`，失败时重新拉取服务端权威数据；项目和任务编辑携带 `version`，冲突后刷新最新版本并提示用户重试。

### 3.6 工作台与历史能力

原描述：

> 完成项目归档、恢复、逻辑删除及历史只读回溯功能，并开发数据概览、近期任务提醒、响应式侧边栏、面包屑和主题切换等工作台能力，提升复杂业务流程下的使用体验。

评价：功能真实，但这一条信息过多，容易成为“功能清单”。简历空间有限时，应降低 UI 功能权重，把“项目状态驱动只读”和“历史追溯”保留即可。响应式侧边栏、面包屑、主题切换可放在项目介绍中口头补充。

建议改为：

> 基于 `active / archived / deleted` 项目状态实现归档、恢复、逻辑删除及历史只读回溯；统一路由元信息驱动标题、面包屑与导航，并适配窄屏侧边栏和明暗主题。

### 3.7 新增 AI 答疑功能是否适合作为项目亮点

可以，而且建议放在项目职责第 4 点。它不是简单调用一次 AI 接口，而是围绕解析结果建立了一个相对完整的前端流式交互：原生 Fetch 处理 SSE 分帧和事件类型，组合式函数维护上下文、增量输出、停止与重试，组件负责 Markdown 展示和滚动体验，Nginx 负责生产环境的长连接转发。这条职责能把项目从“AI 解析 + CRUD”提升为“异步解析后可追问、可验证的工作流”。

但简历中应限定为“接入 AI 答疑”或“实现流式交互”，不要表述为自研大模型、推理服务或完整会话基础设施；模型调用、权限校验、限流、审计和真正的服务端取消仍属于后端或平台能力。

## 五、简历和项目中的风险点

### 5.1 不要说“前端保证了事务”

前端负责生成完整有序集合并调用接口，事务一致性由后端实现。正确表达是“前端采用完整集合提交，后端在事务中统一更新”。

### 5.2 不要把重新请求说成本地回滚

当前排序失败后的处理是重新获取服务端列表，用权威数据覆盖页面状态。它属于“回源恢复”或“重新同步”，不是严格意义上的前端快照回滚。

### 5.3 跨列拖拽不是单个原子操作

跨列拖拽先调用状态更新接口，再调用排序接口。两个请求间可能出现部分成功。可以说明当前通过失败后重新加载保证最终展示与服务端一致；如果继续优化，可设计一个同时提交状态和顺序的批量事务接口。

### 5.4 access token 存在 localStorage 的 XSS 风险

项目采用 Bearer + Cookie 双轨，access token 同时持久化到 `localStorage`。这样便于请求头鉴权，但一旦发生 XSS，token 可被脚本读取。面试时应承认这一取舍，并给出更安全的改进方向：完全使用 `HttpOnly + Secure + SameSite` Cookie 保存认证凭据，前端只读取非 HttpOnly 的 CSRF token；同时配合 CSP、输入输出转义和依赖治理降低 XSS 风险。

### 5.5 “记住密码”明文存储是明显安全问题

当前工具代码把邮箱和密码明文写入 `localStorage`。这不应作为简历能力宣传，正式项目也建议删除。更合理的是仅记住邮箱；长期登录交给 refresh session，密码不应由前端持久化。

### 5.6 当前缺少前端自动化测试

仓库目前主要依靠 `vue-tsc` 和构建检查。若面试官问质量保障，要如实回答，并说明优先补充：请求刷新并发单测、PDF 状态转换单测、排序参数生成单测，以及关键解析链路的端到端测试。

### 5.7 SSE 流式链路的连接与代理风险

AI 答疑使用原生 `fetch`，不复用 Axios 拦截器；401 需要显式调用共享 refresh，再重试一次。生产 Nginx 必须关闭代理缓冲、关闭 gzip，并设置足够的读写超时，否则增量内容可能被攒到最后才返回，或长任务被网关提前断开。SSE 也不是断点续传协议，网络中断后当前实现只能失败重试，不能从上次 delta 继续。

### 5.8 增量内容的安全与上下文边界

模型输出先经 `markdown-it` 转 HTML，再由 DOMPurify 清洗；这降低了 Markdown 注入和 XSS 风险，但不能替代后端提示词隔离、内容审核和权限校验。上下文只取最近 16 条消息并限制 10,000 个字符，属于前端成本控制，不等于服务端完整会话记忆；服务端仍应重新校验 `parse_result_id` 的归属，避免越权读取其他用户的解析结果。

### 5.9 停止生成不等于撤销服务端推理

点击停止只调用 `AbortController`，终止浏览器读取和页面增量渲染；请求已经到达服务端时，模型推理可能继续消耗资源。若需要真正取消，应增加带 request ID 的取消接口或服务端上下文取消机制，并处理取消与 `done/error` 事件同时到达的竞态。

### 5.10 AI 交互成本与可观测性

当前前端没有展示 token 用量、耗时、首字节延迟和请求 ID，也没有自动重连策略。面试中应说明这是体验型答疑功能，后续可增加限流、超时、用量统计、脱敏日志、SSE 心跳和断线兜底查询，避免把“流式显示”夸大为完整的 AI 基础设施。

## 六、可能的项目面试题与参考答案

以下答案按约 40—90 秒口述设计。不要逐字背诵，重点记住“背景、方案、边界、改进”。

### 1. 请用一分钟介绍 TaskPilot

TaskPilot 是一个把任务型文档转换为可执行项目的 AI 辅助平台。用户输入文本或上传文字型 PDF 后，前端先创建文档和异步解析任务，再轮询任务状态；解析完成后用户可以校对标题、交付物、关键要求、风险和任务建议，确认后保存为项目，最后在三列看板中管理任务，并可针对解析结果继续进行 AI 流式答疑。我的重点工作是这条异步业务链路、PDF 多阶段上传、AI SSE 交互、Axios 会话刷新，以及看板排序和乐观锁冲突处理。它和普通后台的区别是，不只是页面 CRUD，而是处理了异步任务、流式响应、部分失败恢复、并发请求和前后端一致性。

### 2. 为什么解析任务采用轮询，没有使用 WebSocket 或 SSE？

解析结果只需要低频地从处理中变为成功或失败，不涉及高频双向通信，所以现阶段用 3 秒一次的短轮询，开发和部署成本更低，也更容易通过普通 HTTP 接口和 Nginx 部署。页面卸载时会清除定时器，并设置最多 100 次的上限，避免无限请求。缺点是有额外请求和最多约 3 秒的状态延迟。如果并发用户或任务时长上升，我会优先考虑 SSE，因为该场景主要是服务端单向推送；同时保留查询接口作为断线重连后的状态兜底。

### 3. 为什么使用递归 `setTimeout`，而不是 `setInterval`？

递归 `setTimeout` 是在本次请求完成后再安排下一次轮询，不会因为接口响应慢而叠加多个未完成请求。`setInterval` 按固定时间触发，如果请求耗时超过间隔，可能产生并发轮询和响应乱序。当前实现还会在成功、失败、超时或组件卸载时停止调度。

### 4. PDF 上传“状态机”是怎么设计的？

我把流程阶段定义成 TypeScript 联合类型，包括 `empty`、`validating`、`ready`、`uploading`、`serverProcessing`、`creatingJob`、`failed`、`cancelled` 和 `succeeded`，所有 UI 文案、按钮禁用、重试能力都从当前阶段派生。选择文件时先校验扩展名、大小和 `%PDF-` 文件签名；提交时创建 `AbortController`，上传完成后保存 `documentId`，再创建解析任务。这样状态转换集中在一个 composable 中，页面不用维护多个互相矛盾的 boolean。

### 5. 为什么不用几个 boolean 表示上传状态？

多个 boolean 很容易出现非法组合，例如 `uploading=true` 的同时 `failed=true`，而联合类型一次只能处于一个主阶段。它还能让 TypeScript 在 `switch` 中帮助检查分支，使按钮权限和提示文案更容易维护。如果状态进一步复杂到包含并行子状态、事件约束和可视化需求，我会考虑引入 XState；当前规模用轻量实现更合适。

### 6. 上传失败后如何做到分阶段重试？

关键是区分“文件还没上传成功”和“文档已经保存但创建任务失败”。上传成功后会保留服务端返回的 `documentId`。用户重试时，如果已有 `documentId`，就跳过文件上传，直接创建解析任务，避免重复传输和生成重复文档。如果服务端提示该文档已有活跃任务，前端会查询最新任务并继续原流程。这个设计相当于利用服务端资源 ID 作为恢复点。

### 7. `AbortController` 真正取消了什么？

前端把 `signal` 传给 Axios 请求，调用 `abort()` 后浏览器会中止等待该 HTTP 请求，Axios 将其识别为取消错误，页面进入 `cancelled` 状态。它能取消客户端请求和后续处理，但不保证服务端已经开始的工作一定停止；请求到达服务端后是否响应取消，需要后端根据连接断开或上下文取消主动终止。因此我不会把它表述成“保证撤销服务端操作”。

### 8. 并发多个请求同时返回 401 时如何处理？

第一个 401 将 `isRefreshing` 设为 true 并发起 refresh，之后的 401 不再刷新，而是把原请求的 resolve/reject 放入等待队列。刷新成功后更新 access token，队列中的请求统一写入新 token 并重放；刷新失败则统一 reject，并由注入的会话失效处理器清理 Pinia 和本地状态、跳转登录页。原请求还带 `_retried` 标记，避免重试后仍 401 时无限循环。

### 9. 为什么 refresh 请求不能复用普通的业务请求封装？

refresh 本身也可能返回 401。如果它和普通受保护接口完全走同一套自动刷新逻辑，就可能出现 refresh 失败后再次触发 refresh 的递归循环。因此代码显式识别 refresh URL，让它的 401 直接判定为会话失效。更彻底的写法也可以创建一个不挂载刷新响应拦截器的独立 Axios 实例。

### 10. CSRF 和 XSS 有什么区别？项目如何处理？

CSRF 是利用浏览器自动携带 Cookie，以用户身份发起非预期请求；项目由后端下发一个前端可读取的 CSRF Cookie，前端把它回填到 `X-CSRF-Token`，后端校验 Cookie 和请求头是否匹配。XSS 是恶意脚本进入页面并执行，CSRF token 不能防 XSS。当前 access token 存在 localStorage，仍有被 XSS 读取的风险；更安全的方案是认证凭据全部使用 HttpOnly Cookie，再结合 CSP、转义和依赖安全治理。

### 11. 路由守卫和后端鉴权分别负责什么？

路由守卫主要负责前端访问体验：启动时等待会话探测，未登录访问受保护页面时跳到登录页并记录 redirect，已登录访问登录页则回到工作台。真正的身份和资源权限必须由后端校验，因为用户可以绕过前端直接请求接口。Axios 拦截器负责携带凭据和处理过期，不等同于权限判断。

### 12. 看板拖拽排序是怎么计算插入位置的？

拖拽经过某一列时，我获取该列除被拖卡片之外的卡片 DOM，比较鼠标 Y 坐标和每张卡片的垂直中点；鼠标位于某卡片中点之上，就把该位置作为插入索引，否则插到列尾。页面展示占位符，drop 时从目标数组移除原卡片，再插入计算位置。除拖拽外还保留上移、下移按钮，便于移动端和键盘操作。

### 13. 为什么排序接口提交全部任务 ID，而不是只提交两个任务？

只交换两个任务看起来请求更小，但长期容易出现重复序号、顺序空洞和并发更新难以校验的问题。当前前端生成项目内完整有序 ID 集合，后端可以校验集合是否完整、是否属于同一项目，再在事务中按数组下标统一写入 `sort_order`。代价是任务很多时请求和更新量会增加；大规模场景可以改为稀疏排序值或 fractional indexing，并配合版本号解决并发。

### 14. 排序失败是如何回滚的？

严格来说当前不是前端快照逆操作，而是回源恢复。页面会先形成新的本地顺序并提交；接口失败后重新请求任务列表，用服务端权威顺序覆盖本地状态。这样能保证最终显示一致，但会多一次请求。跨列拖拽还包含状态更新和排序两个接口，并非原子操作；更理想的改进是提供一个同时提交目标状态与完整顺序的后端事务接口。

### 15. 乐观锁如何工作？为什么适合这个项目？

项目和任务数据都带 `version`。编辑时前端提交当前版本，后端更新条件包含 ID 和 version；更新成功后版本递增，如果影响行数为零，说明数据已被其他操作修改，返回冲突错误。前端识别冲突码后重新拉取最新数据并提示用户重试。它适合冲突概率较低的管理系统，不需要长时间锁住数据；缺点是冲突时用户改动不会自动合并，目前采取刷新后重填的保守策略。

### 16. Pinia、composable 和 API 层是怎么分工的？

API 层只描述接口、参数和返回类型，并处理通用 HTTP 行为；Pinia 按业务域保存跨页面或需要在路由跳转后继续使用的数据，例如当前解析任务、解析结果、项目和任务；页面私有的复杂交互流程放 composable，例如 PDF 上传阶段和取消控制。依赖方向保持为 view/layout 到 store，再到 API 和 utils，避免页面直接散落请求，也避免 API 反向依赖 router 或 store。会话失效通过回调注入到 `main.ts`，就是为了避免循环依赖。

### 17. 项目中 `Promise.all` 和 `Promise.allSettled` 分别用在什么地方？

加载项目和任务时两者都是页面成立的核心数据，任一失败都无法正常展示，所以使用 `Promise.all`，并行请求且快速失败。加载来源文档和解析结果属于补充信息，即使其中一个失败，项目看板仍可使用，所以使用 `Promise.allSettled` 分别读取成功结果。这体现了是否快速失败应由业务依赖关系决定，而不是所有并行请求都固定使用一种方法。

### 18. 如果让你继续优化这个项目，优先做什么？

我会优先做三件事。第一，删除 localStorage 明文记住密码，并评估改为纯 HttpOnly Cookie 会话，降低 XSS 风险。第二，为 Axios 并发刷新、PDF 状态转换和排序参数生成补单元测试，再给主链路补端到端测试。第三，把跨列状态变更与排序合并为一个后端事务接口；如果解析任务规模上升，再将轮询升级为 SSE，并保留查询接口用于断线恢复。

### 19. 为什么 AI 答疑使用 SSE，而不是 WebSocket？

这里是客户端发起一次问题、服务端持续单向返回 token，SSE 基于普通 HTTP，接入现有鉴权、Nginx 和负载均衡更简单；WebSocket 适合双向实时协作，但连接管理和部署成本更高。当前仍保留普通 HTTP 错误响应和解析结果查询作为兜底，SSE 断开时提示重试。

### 20. 你如何解析不完整的 SSE 数据帧？

`ReadableStream` 每次 `read()` 得到的 chunk 不保证以事件边界结束，因此先用 `TextDecoder` 解码并追加到 buffer，再按空行拆分完整事件，保留最后一个不完整片段到下一次读取；同一事件的多行 `data:` 合并后再按事件类型解析。流结束前没有收到 `done` 就视为异常中断。

### 21. 多轮上下文如何控制长度？会不会泄露无关内容？

发送前只筛选已完成且允许进入上下文的消息，最多取最近 16 条，并按 Unicode 字符数裁剪到 10,000；当前用户问题最后追加。这个限制只是前端预算，后端必须按解析结果 ID 做归属和权限校验，并在服务端再次限制 token、脱敏和提示词边界。

### 22. Markdown 渲染为什么还要 DOMPurify？

Markdown 转 HTML 会产生 `a`、表格等标签，若允许原始 HTML 或危险属性，模型输出就可能成为 XSS 载体。因此关闭 `html`，再用 DOMPurify 过滤脚本、嵌入标签和事件属性。安全策略应继续配合 CSP 和后端输出约束，不能只依赖前端清洗。

### 23. AI 请求如何处理 401？为什么不能直接依赖 Axios 拦截器？

流式请求使用原生 `fetch`，不会经过 Axios 响应拦截器，所以 API 层显式检查 401，调用共享 `refreshAccessToken()` 后携带新 token 重试一次；refresh 明确返回 401/403 时通过统一会话失效回调清理状态，网络错误与 5xx 则保留登录态。重试次数必须受限，避免 refresh 递归和重复创建流。

### 24. 用户停止生成时，前端状态如何避免被旧数据回写？

每次生成创建独立 `AbortController`，停止后将请求识别为取消并把消息置为 `stopped`；组件卸载时也会 abort 并清理定时器。需要强调这只保证客户端不再消费旧流，不能保证服务端停止推理；真正取消需要后端支持 request ID。

### 25. AI 答疑功能上线前你会补哪些测试？

优先测试 SSE 分帧（跨 chunk、跨行、缺少 `done`）、`meta/delta/error` 事件处理、401 refresh 后只重试一次、停止和卸载时不再更新 UI、上下文裁剪，以及 Markdown 清洗。再用端到端测试覆盖“打开助手—提问—流式完成—失败重试”的主链路，并验证 Nginx 不缓冲响应。

结合过去面经中暴露的薄弱点，TaskPilot 面试前还应能稳定回答：

- 浏览器事件循环，Axios Promise 回调、定时轮询分别进入什么队列。
- `localStorage`、Cookie、HttpOnly、SameSite、Secure 的区别。
- 强缓存、协商缓存，以及 Vite 构建产物适合怎样的缓存策略。
- 从输入线上 TaskPilot URL 到页面展示发生了什么。
- Vite 开发代理和生产 Nginx 反向代理分别解决什么问题。
- TypeScript 联合类型、类型收窄、泛型请求方法和声明文件基础。
- 大任务列表出现数万 DOM 时如何用虚拟列表、分页或分组降低渲染压力。
- 前端如何监控接口失败率、解析耗时、白屏、LCP、INP 和 JS 异常。

## 八、面试表达建议

回答项目题时建议采用固定四段式：

1. **背景：** 用户遇到了什么流程或异常场景。
2. **方案：** 数据结构、状态、请求顺序和关键 API 如何设计。
3. **结果：** 避免了什么重复操作，保证了什么一致性或体验。
4. **边界：** 当前方案的限制，以及下一步如何改进。

例如不要只说“我用了 AbortController”，而要说“上传可能耗时且用户会换文件，所以把 signal 贯穿到 Axios；取消后停止等待并阻止旧请求回写状态，但服务端已开始的处理不保证被撤销”。这种回答更像真正理解过工程边界，而不是只记住 API 名称。
